# 서울 침수흔적 3D: 서울 전역 건물 웹 3D 스트리밍 뷰어

> 국토교통부 GIS건물통합정보와 서울시 침수흔적도를 결합해, 서울 전역 건물을 OGC 3D Tiles 1.1 타일셋으로 변환하고 Three.js로 직접 만든 스트리밍 렌더러로 표시하는 프론트엔드 포트폴리오입니다. 침수 이력이 있는 지역의 지하층 주거 건물 후보를 건물 단위로 걸러 볼 수 있습니다.

## 1. 프로젝트 개요

본 프로젝트는 서울 전역 건물 【 】만 동을 브라우저에서 끊김 없이 탐색할 수 있도록 만든 3D 스트리밍 뷰어입니다.

건물 데이터를 미리 OGC 3D Tiles 1.1 타일셋(glTF/GLB, 쿼드트리 계층)으로 변환합니다. 브라우저에서는 Three.js로 직접 구현한 렌더러가 화면 오차를 계산해 지금 필요한 타일만 불러오고, 정해진 메모리 예산 안에서 타일을 보관·해제합니다. 같은 타일셋을 CesiumJS로도 띄워, 같은 카메라 경로에서 성능을 비교합니다.

그 위에 서울시 침수흔적도(2010~2025)를 겹쳐, 침수 이력이 있으면서 지하층이 있는 주거 건물을 현장 확인 후보로 표시합니다.

화면은 세 단계로 구성됩니다.

1. **건물 스트리밍**: 서울 전역 건물을 LOD1 블록 모델로 표시
2. **+ 침수흔적**: 선택한 연도의 침수 구역을 바닥에 표시하고, 겹치는 건물을 색칠
3. **+ 지하층 주거 조건**: 침수 이력 AND 지하층 AND 주거인 건물만 후보로 강조

## 2. 문제 배경

2022년 8월 서울 남부권에 시간당 100mm가 넘는 집중호우(동작구 신대방동 시간당 141.5mm)가 내리면서 반지하 주택 침수 피해가 컸습니다. 이후 서울시는 반지하 주택 전수조사와 침수방지시설 설치를 추진하고 있지만, 다음과 같은 문제가 남아 있습니다.

- **확인할 대상이 많습니다.** 서울시 정보공개 자료에 따르면 반지하 주택 23만 7619호 중 2만 8439호(12%)가 차수시설·피난시설 같은 침수방지시설이 필요한 것으로 나타났습니다.
- **설치와 점검이 아직 끝나지 않았습니다.** 2024년 6월에도 물막이판이 없는 서울 반지하가 약 8000가구라는 보도가 있었습니다.
- **근거가 되는 지도가 서로 다릅니다.** 서울시가 공개한 침수흔적도 면적의 60%가 행정안전부 생활안전지도에는 빠져 있다는 보도가 있었습니다. 어떤 지도를 기준으로 볼지 실무에서도 정리되지 않은 상태입니다.
- **필요한 정보가 흩어져 있습니다.** 침수 이력은 침수흔적도(영역 데이터)에, 지하층수·용도는 건물 데이터에 따로 있습니다.

현장 확인 뒤에는 실제 조치가 이어집니다. 서울시는 침수방지시설(물막이판·역류방지기)의 설치·작동 여부를 점검하고, 없으면 담당자가 현장을 방문해 무상으로 설치합니다. 점검 결과에 따라 관리 등급을 나누고, 장마철 임시 이주나 공공임대주택 이주(주거상향)도 지원합니다. 다만 2024년에도 최우선 관리 대상 약 1만 5천 가구를 건축사 300여 명이 10일간 점검했을 만큼, 대상은 많고 인력과 시간은 한정되어 있습니다.

따라서 침수 이력이 있는 지역의 지하층 주거 건물을 한 화면에서 빠르게 골라 보고, 연도별로 비교하면서 출처를 함께 확인할 수 있는 도구가 현장 확인 대상을 정하는 데 필요합니다.

## 3. 문제 정의

### 3.1 업무 관점

- 침수흔적도는 영역(폴리곤) 데이터이고, 지하층수·용도는 건물 데이터에 있습니다. 두 데이터가 따로 있어 "침수 이력이 있는 곳의 지하층 주거 건물"을 한 화면에서 바로 볼 수 없습니다.
- 침수 범위는 연도마다 다릅니다. 연도를 바꿔 가며 비교하려면 매번 다시 계산해야 합니다.

### 3.2 기술 관점

- 서울 전역 건물을 한 번에 불러오면 첫 화면이 늦게 뜨고, 받은 데이터를 해석하는 동안 화면이 멈추며, 메모리가 계속 쌓입니다.
- 어떤 타일을 언제 받고 언제 버릴지 정하지 않으면, 화면에서 몇 픽셀로 보이는 먼 지역까지 세밀하게 그리느라 자원을 씁니다.
- 건물들을 하나로 합쳐(병합) GPU 호출 수(draw call)를 줄이면, 이번에는 건물 하나만 골라 색칠하거나 클릭할 수 없게 됩니다.

구체적인 수치는 7장에 기록합니다.

## 4. 프로젝트 목적과 범위

### 4.1 목적

- 서울 전역 건물을 표준 형식(OGC 3D Tiles 1.1)으로 변환하고, 타일 선택(화면 오차 기준 LOD)과 캐시(메모리 예산)를 Three.js로 직접 구현한 스트리밍 렌더러를 만듭니다.
- 같은 타일셋·같은 카메라 경로에서 CesiumJS와 수치로 비교합니다.
- 병합된 건물 위에서도 침수 이력·지하층·용도 조건으로 건물 단위 필터를 즉시 적용합니다.

### 4.2 하지 않는 것

- **침수 시뮬레이션**: 수리 모델 없이 수위를 계산하면 결과가 왜곡됩니다. 기록된 침수흔적만 사용합니다.
- **반지하 가구 판정**: 데이터에는 가구 정보가 없습니다. "지하층이 있는 주거 건물 후보"까지만 표시합니다.
- **위험도·위법 판정**: 후보는 현장 확인 대상을 고르기 위한 화면용 분류입니다.
- **지형 반영**: 건물은 평면 위에 세웁니다(한계는 10장).

### 5.2 데이터 가공 (타일러)

원본을 그대로 쓰지 않고, 브라우저가 빠르게 읽을 수 있는 3D Tiles 타일셋으로 미리 가공합니다.

| 가공 데이터            | 저장 위치                      | 설명                                                                                                                                                                        |
| ---------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `featureId`            | glTF `EXT_mesh_features`       | 건물마다 붙인 번호. 병합된 메시 안의 모든 꼭짓점(바닥·벽·지붕)에 저장해 건물을 구분                                                                                         |
| `floodYears`           | glTF `EXT_structural_metadata` | 건물 바닥면이 겹치는 침수흔적 연도 (연도별 비트, 자리 번호 = 연도 − 2010). UINT16(16자리)이라 2010~2025만 담을 수 있고, 범위 밖 연도를 넣으면 타일러(s04)가 멈춤                |
| `grndFlr` / `ugrndFlr` | glTF `EXT_structural_metadata` | 지상·지하 층수                                                                                                                                                              |
| `usage`                | glTF `EXT_structural_metadata` | 주용도 (주거 여부 판정용)                                                                                                                                                   |
| `height`               | 지오메트리                     | 3D 돌출 높이. ① 높이(`A16`)가 있으면 그대로 ② 없고 지상층수가 있으면 층수 × 3.25m ③ 둘 다 없으면 3.25m(1층). 3.25m는 높이·층수가 모두 있는 305,600동의 "높이 ÷ 층수" 중앙값 |
| `heightSource`         | glTF `EXT_structural_metadata` | 높이를 어디서 얻었는지(원본 / 층수 추정 / 기본값). ③은 후보에서 제외하고 상세 패널에 "높이 정보 없음" 표시. 침수 보기 색은 다른 건물과 같음                                 |
| 타일 계층              | `tileset.json`                 | 쿼드트리 레벨과 위치. 부모 타일에는 큰 건물만, 자식 타일에는 나머지 건물을 담음 (3D Tiles의 ADD 방식 세분화)                                                                |
| `geometricError`       | `tileset.json`                 | 이 타일까지만 그렸을 때 빠진 건물 중 가장 큰 크기(미터). 렌더러가 이 값을 화면 픽셀로 바꿔 자식 타일을 받을지 정함                                                          |
| 타일 중심              | 타일 `transform`               | 꼭짓점은 타일 중심 기준 상대좌표로 저장 (float32 정밀도 대응)                                                                                                               |

### 5.3 판정 기준

```txt
침수 이력 있음
- 건물 바닥면이 선택한 연도의 침수흔적에 닿음 (면적이 작아도 포함)
- 그리고 사용승인일자가 그 연도 이전 (나중에 지은 건물은 제외)

후보 (모두 만족)
- 침수 이력 있음
- 지하층수 ≥ 1 (건축물대장 기준. 반지하도 건축법상 지하층에 포함)
- 주용도: 단독주택(01000) 또는 지상 4층 이하 공동주택(02000)
  공동주택은 코드로 아파트를 나눌 수 없어, 건축법 시행령 별표1의 기준
  (주택으로 쓰는 층수 5개 층 이상 = 아파트)을 지상층수로 근사해 아파트를 제외
  (아파트 지하는 대부분 주차장)
```

건물 데이터는 최신 시점(2026-10-09)이고 침수흔적은 2010~2025년이라 시점이 다릅니다. 이 화면은 지금 있는 건물을 현장 확인하기 위한 것이라 최신 건물을 쓰고, 나중에 지은 건물은 사용승인일자로 걸러 과거 침수 이력이 잘못 붙지 않게 했습니다. 사용승인일자가 빈 건물은 침수 후보에서 빼지 않습니다. 날짜가 없다는 것은 정보가 없다는 뜻이지 침수와 무관하다는 뜻이 아니기 때문입니다.

"닿기만 해도 포함"으로 정한 이유는, 이 화면의 목적이 현장 확인 대상을 고르는 것이라 놓치는 쪽이 더 위험하기 때문입니다. 관악구(2022년)에서 겹친 면적이 1㎡ 미만인 후보는 183동(경계선만 맞닿은 0㎡ 건물은 0동)이며, 이들을 빼면 후보는 3,251동에서 3,068동이 됩니다. 도형 경계 오차일 가능성이 있지만 포함했습니다.

후보는 실제 위험도나 행정적 우선순위가 아니라, 현장 확인 대상을 고르기 위한 화면용 분류입니다.

## 6. 구조

```txt
[속성 스키마: schema/building.json (3D Tiles 메타데이터 스키마 형식, 단일 원본)]
  → Python: 저장 직전 컬럼 이름·타입 검사
  → Node: GLB 속성표(EXT_structural_metadata) 스키마로 그대로 사용
  → TypeScript: 생성 스크립트로 building.d.ts 생성 (타일러·렌더러 공용)

[실행 전 ①: 데이터 정리 (Python)]
건물 SHP ──┐
           ├─ CP949 읽기 → 좌표계 통일 → 깨진 도형 보정 → 침수 겹침 계산
침수흔적 SHP ┘   → 높이·후보 속성 계산 → 개별 피해 정보 제거
                → 위경도(WGS84) FlatGeobuf 저장

[실행 전 ②: 타일 만들기 (Node · TypeScript)]
FlatGeobuf → 쿼드트리 분할 → 타일별 삼각분할(earcut)·병합
          → GLB 저장 (glTF Transform, feature ID·속성 포함)
          → tileset.json 작성 (타일 계층·geometricError) → 3d-tiles-validator로 검증

[실행 중: 내 렌더러 (Three.js)]
카메라 → 화면 오차 계산으로 그릴 타일 선택 → 필요한 타일 요청
      → Worker에서 GLB 파싱 → 메인 스레드에서 GPU 업로드
      → 셰이더가 feature ID로 건물 상태를 보고 색 결정 → 화면
      └ 메모리 예산 초과 시 오래 안 쓴 타일부터 해제 (LRU)

[비교 기준: CesiumJS]
같은 tileset.json → Cesium3DTileset → 같은 카메라 경로로 측정
```

- 타일셋은 OGC 3D Tiles 1.1 표준을 따르므로 CesiumJS 같은 다른 뷰어에서도 그대로 열립니다.
- 3D Tiles는 지구 중심 좌표(ECEF)를 기준으로 하므로, 내 렌더러는 서울 중심 기준의 지역 좌표로 바꿔 씁니다.
- CesiumJS가 내부에서 해 주는 타일 선택(`maximumScreenSpaceError`)과 캐시(`cacheBytes`)에 해당하는 부분을 직접 구현했습니다.

렌더러 실행 (`renderer/`, Vite):

```bash
cd renderer && npm install && npm run dev
# http://localhost:5173/?region=gwanak&at=zoom   (at: bench/path.json 구간 이름, 그 구간 끝 지점으로 카메라)
```

### 7.4 측정 절차

두 렌더러를 같은 장치(`bench/`)와 같은 경로(`bench/path.json`)로 잽니다. 재생기·기록기는 렌더러를 모르고, 렌더러마다 다른 부분은 어댑터(`bench/adapters/`) 하나에만 있습니다.

- 경로: overview(서울 전체에서 멈춤) → zoom(신림동으로 내려감) → alley(관악 → 동작) → return(서울 전체로 올라감)
  - 카메라 위치는 프레임 수가 아니라 경과 시간으로 계산합니다. FPS가 달라도 시각 t의 카메라는 같습니다.
  - 위경도·방향은 선형으로, 높이는 로그 공간에서 보간합니다(일정 속도, 이징 없음). 재생 중에는 마우스 입력을 끕니다.
- 측정 화면: `?bench=1` (기본 `seoul`, `&region=gwanak`으로 변경). 바탕 지도·지구본·하늘·대기 효과는 끄고 건물만 그립니다. 타일셋 옵션은 기본값 그대로 두고, 그 값을 결과 JSON에 기록합니다.
- 캔버스는 1680×928로 고정합니다. 창이 이보다 작으면 측정 화면이 경고를 띄우고 재생을 막습니다(잘린 캔버스로 재지 않게). 결과 JSON `env.canvasFixed`에 고정 여부가 남습니다. 평소 화면은 창 크기를 따라갑니다.
- 경로 지점 정하기: 평소 화면(바탕 지도 켜짐)에서 카메라를 맞추고 "현재 카메라 값 복사" → `path.json`에 붙여 넣기

```bash
node bench/compress-tiles.mjs   # 루트에서. data/tiles/**의 .glb·.json 옆에 .br·.gz를 미리 만듦(원본 그대로, 타일러를 다시 돌린 뒤에만)
node bench/serve.mjs            # http://localhost:8080/viewer/cesium-check.html?bench=1
```

- `bench/serve.mjs`는 `python -m http.server 8080`과 포트·경로가 같고, 바뀌는 건 압축뿐입니다. 요청의 `Accept-Encoding`을 보고 미리 만든 `.br` → `.gz` → 원본 순으로 골라 `Content-Encoding`을 붙여 보냅니다.
  - 요청마다 압축하지 않는 이유: 압축하는 CPU 시간이 측정에 섞이기 때문입니다.
  - python과 같게 맞춘 것: 요청마다 연결을 새로 맺음(`Connection: close`, python은 HTTP/1.0), `Last-Modified`·`If-Modified-Since` → 304, `.glb`의 `Content-Type`(`application/octet-stream`).
- 결과 JSON `env.transfer`에 실제로 받은 압축 방식(`tileset.json` 응답의 `Content-Encoding`)과 재생 중 타일 요청 바이트(전송·압축 본문·원본, 압축돼서 온 요청 수)가 남습니다.
- 주의: python 서버 때 받은 타일이 브라우저 HTTP 캐시에 남아 있으면, 파일 수정 시각이 같아 서버가 304로 답하고 브라우저는 압축 안 된 사본을 그대로 씁니다. 첫 방문은 "Disable cache"를 켜고 재므로 괜찮고, 결과 JSON `env.transfer.compressedRequests`가 0이면 압축 없이 받은 회차입니다.
- 압축 전송으로 잰 결과는 `bench/results/cesium-br/<조건>/`에 둡니다. summarize 제목에는 `cesium-br/fast4g`처럼 `bench/results` 아래 경로가 조건으로 나옵니다.

1. **첫 방문**: DevTools Network의 "Disable cache"를 켜고 새로고침 → 회차(1~3) 고르기 → 재생 → "JSON 다운로드"
2. **재방문**: 새로고침 없이 같은 화면에서 재생 한 번 더 → "JSON 다운로드" (렌더러 메모리에 타일이 남은 상태)
3. 1~2를 3번(회차 1·2·3) → 결과 파일 6개 `{renderer}_{region}_{first|revisit}_{n}.json`을 네트워크 조건(DevTools throttling) 폴더 `bench/results/<조건>/`로 옮기기 (예: 제한 없음은 `bench/results/localhost/`, Fast 4G는 `bench/results/fast4g/`). 결과 JSON에 조건 칸이 없어서 폴더 이름이 곧 조건 기록이고, `bench/results/` 바로 아래에 두면 summarize가 읽지 않습니다.
4. `node bench/summarize.mjs bench/results/<조건>` → 그 조건의 묶음별 3회 평균 표. 제목에 `bench/results` 아래 폴더 경로를 조건으로 표시합니다. 경로가 다른 결과가 섞이면 멈추고, 구간 끝 카메라가 회차끼리 얼마나 다른지(m)도 같이 출력합니다.

재생 중 탭 전환·창 가림으로 브라우저가 렌더를 멈추면 그 회차는 렌더러 성능이 아닙니다. 재생 중 화면이 숨거나(`visibilitychange`) 1초 넘는 프레임 간격이 있으면 결과 JSON에 `valid: false`와 사유를 남기고, summarize는 그 파일을 평균에서 빼고 경고합니다. 그 회차는 다시 잽니다.

반면 재생이 끝날 때까지 첫 화면 타일 로드가 끝나지 않은 회차는 빼지 않습니다. 느린 것도 렌더러 성능이므로, 빼면 평균이 실제보다 빨라 보입니다. 결과 JSON에 `initialTilesPending: true`를 남기고, summarize는 첫 화면 시간을 평균 대신 `> 재생 시간 (미완료 n/3)`으로 표시합니다(다른 지표는 그대로 평균).

구간마다 기록하는 값: 프레임 수, 평균·최대 프레임 간격, 느린 프레임 비율(33.3ms 초과), 한 프레임 작업 시간(평균·p95·최대), 불러온·내린 타일 수, 구간 끝 대기 요청 수와 타일 메모리. 전체: 재생 시작 → 첫 화면 타일 로드 완료(initialTilesLoaded)까지 걸린 시간. 캔버스 크기, devicePixelRatio, 브라우저, 렌더러 버전도 같이 남깁니다.

- 프레임 간격은 화면 주사율에 묶입니다(60Hz면 일이 적어도 16.67ms). 그래서 렌더러가 한 프레임에 실제로 쓴 시간을 따로 잽니다. CesiumJS는 `scene.preUpdate` ~ `scene.postRender` 사이입니다.
- 작업 시간은 메인 스레드 CPU 시간입니다. GPU가 실제로 그리는 시간과 프레임 사이의 비동기 작업(타일 응답 처리 등)은 들어가지 않으므로, 사용자가 보는 끊김은 프레임 간격으로 봅니다.

**시간 분해** (Fast 4G 프리셋: 다운로드 9 Mbps × 0.9 = 1,012,500 B/s, 지연 60ms × 2.75 = 165ms. Chrome DevTools 소스 `NetworkManager.ts` 기준)

## 8. 주요 기능

### 건물 스트리밍

서울 전역 건물을 LOD1 블록 모델로 표시합니다. 카메라 시야에 들어오는 타일만 불러오고, 화면에서 작게 보이는 지역은 큰 건물만 표시합니다(화면 오차 기준 LOD).

### 침수흔적 레이어

14개 연도 중 하나를 골라 침수 구역을 바닥에 표시합니다. 연도를 바꾸면 지오메트리를 다시 만들지 않고 셰이더 조건값만 바꿔 즉시 반영합니다.

### 표시 모드

- **침수 보기**: 침수흔적과 바닥면이 겹치는 건물을 파랑으로 표시합니다.
- **후보**: 침수 이력 AND 지하층 AND 주거인 건물만 주황으로 표시하고(높이 정보가 없는 건물은 제외), 나머지는 회색으로 낮춥니다(ISA-101 High Performance HMI).

### 건물 상세

건물을 클릭하면 용도, 지상·지하 층수, 침수 이력 연도를 보여줍니다.

### 하단 지표

침수흔적 겹침 【 】동 → 그중 지하층 있음 【 】동 → 그중 주거(후보) 【 】동을 단계별로 보여줍니다. 선택한 연도, 출처, 수정일을 함께 표기합니다.

### 성능 표시와 비교 재생

FPS, draw call, 로드된 타일 수, 타일 메모리를 화면에 표시합니다. 같은 카메라 경로를 자동 재생하고, 렌더러를 내 렌더러 / CesiumJS로 바꿔 같은 조건에서 비교할 수 있습니다.

## 9. 기술 스택

- Three.js
  - 자체 스트리밍 렌더러: 화면 오차 기준 타일 선택, 메모리 예산 캐시(LRU), 셰이더 필터, GPU picking
  - 위경도 ↔ ECEF·ENU 변환은 타일러와 같은 공용 모듈(`shared/geo.ts`)을 씁니다. 타일을 만든 공식으로 그립니다
- CesiumJS
  - 비교 기준. 같은 타일셋을 `Cesium3DTileset`으로 띄워 같은 조건에서 측정
- Vite + React
  - 앱 틀과 UI 상태 관리. 페이지 전환·검색 노출이 필요 없는 단일 화면이라 Next.js 대신 선택
- TypeScript
  - 타일·건물 속성 타입 정의
- Web Worker
  - GLB 파싱을 메인 스레드 밖에서 처리 (Transferable로 복사 없이 전달)
- Python (타일러 ①: 데이터 정리)
  - geopandas·shapely·pyproj·pyogrio(GEOS·PROJ·GDAL 기반)로 SHP 읽기, 좌표계 통일, 깨진 도형 보정, 침수 겹침 계산. 결과는 FlatGeobuf로 저장
- Node · TypeScript (타일러 ②: 타일 만들기)
  - flatgeobuf로 읽기, earcut으로 삼각분할, glTF Transform으로 GLB 작성(EXT_mesh_features·EXT_structural_metadata), 3d-tiles-validator로 검증. 렌더러와 같은 언어라 속성 이름·타입을 공유
- OGC 3D Tiles 1.1 / glTF (GLB)
  - 타일 형식. 건물 번호는 `EXT_mesh_features`, 속성은 `EXT_structural_metadata`
- Tailwind CSS / shadcn/ui
  - UI 스타일링과 컴포넌트
- 호스팅
  - 타일: Cloudflare R2 (잠정, 타일 총용량 확인 후 확정) / 앱: 【 】
- npm
  - 패키지 매니저. 타일러(`tiler/node`)와 렌더러(`renderer`) 모두 `package-lock.json`으로 버전 고정

## 10. 한계

- 지형(고도)을 반영하지 않아, 경사지 건물도 평면 위에 세웁니다.
- 침수흔적도는 기록된 범위이며, 기관별 지도 간 차이가 보도된 바 있습니다. 화면에 연도·출처·수정일을 표기합니다.
- 지하층 여부는 건축물대장에 적힌 값(GIS건물통합정보가 세움터 건축물대장 속성을 통합한 것)을 그대로 씁니다. 현장과 다를 수 있으며, 같은 대장에서 나온 값이라 다른 데이터로 교차 검증하지 못했습니다.
- 오피스텔은 실제로 주거에 많이 쓰이지만, 용도코드가 대분류(업무시설 14000)만 있어 일반 사무실과 구분할 수 없습니다. 업무시설 전체를 넣으면 지하주차장이 있는 사무실이 후보로 섞이므로 제외했습니다.
- 지하층이 있다고 반지하 주거가 있는 것은 아닙니다. 실제 거주 여부와 침수방지시설 설치 여부는 현장 확인이 필요합니다.
- 공동주택의 아파트 제외는 지상층수로 근사한 것이라, 필로티가 있는 다세대처럼 층수 기준과 법적 구분이 다른 건물이 섞일 수 있습니다.
- 건축물대장 속성이 없는 도형은 용도·층수를 몰라 후보 판정에서 빠지고, 기본 높이(3.25m)로 그립니다. 침수 이력은 도형으로 계산하므로 그대로 표시합니다.
- 침수 이후 철거된 건물은 최신 건물 데이터에 없어 표시되지 않습니다.
- 사용승인일자(A13)가 비어 있는 건물이 많습니다(서울 전체 22%, 151,411동). 관악구는 17%(6,655동)가 빈칸이고 가장 최근 값이 2021-07-27이라, 침수 이후 지은 건물을 거르는 규칙이 관악에서는 실제로 걸러내는 건물이 없습니다. 2022 침수 구역에 닿은 관악 6,006동 중 1,141동은 사용승인일자가 비어 있어 그대로 남겼습니다. 서울 전체에서는 이 규칙으로 2022년 3동이 걸러지고, 2025년은 0동입니다.
- "닿기만 해도 포함" 기준 때문에 실제 침수 영향이 작은 건물도 후보에 들어갈 수 있습니다.
- CesiumJS 비교는 건물 타일만 그리는 조건(지구본·영상 끔)에 한정한 결과이며, 범용 엔진 전체의 성능 비교가 아닙니다.
